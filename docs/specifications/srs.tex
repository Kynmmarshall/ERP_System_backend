\section{Purpose, scope and stakeholder goals}
\subsection{Purpose}
This Software Requirements Specification (SRS) establishes the review baseline
for the ICT University multi-tenant Enterprise Resource Planning system.
It states what the system must do, its boundaries, observable acceptance conditions
and unresolved obligations. The companion Software Design Document (SDD) explains
how the current implementation realizes those requirements.

\subsection{Product scope}
The product integrates three business domains through four FastAPI services:
Identity; Academic; Finance \& Marketing; and Administration \& HR. A shared Nginx
gateway exposes versioned HTTP APIs. A PostgreSQL cluster hosts four separately
owned databases. RabbitMQ carries the enrollment-to-invoice workflow.
The React frontend is maintained in the sibling \code{ERP_System} repository.
Both repositories were inspected; the baseline distinguishes functional self-service
screens from administrative placeholders.

\subsection{Success criteria}
Demonstrate one complete asynchronous business transaction across modules;
tenant and role isolation; reliable financial recording; the required domain
workflows; test evidence; and reproducible deployment/documentation.
Production readiness additionally requires the unresolved release gates in
Section~\ref{sec:acceptance}, not merely a successful local demonstration.
\callout{Requirement authority}{The supplied SEN4121 brief defines the mandatory
scope. Where the code implements only part of that scope, both the obligation and
the gap are retained. An implemented handler is not evidence that every concurrency,
security, UI or operational acceptance condition has passed.}

\section{Product context, actors and constraints}
\subsection{Boundary and external systems}
Browsers call one gateway origin. The frontend supplies role-gated self-service screens and
401-driven session restoration; the backend remains authoritative for authorization.
The mobile-money integration is an external provider adapter, not a fifth ERP
service. Jenkins, a container registry, host TLS termination and an off-host backup
repository belong to the operating environment rather than to business modules.
Only the registry and TLS configuration intentions are represented in deployment
assets; a functioning production environment is not established by these documents.

\subsection{Mandatory constraints}
\begin{enumerate}
\item At least three independently deployable business services, each owning its
database/schema. The baseline uses four databases, with Identity as the fourth service.
\item An API gateway performs routing, authentication delegation and rate limiting.
\item At least one cross-module workflow uses asynchronous broker messaging.
\item Dockerfiles and Compose orchestration support the full system; Kubernetes is optional.
\item A CI pipeline runs tests and builds images on main-branch changes; its repository
trigger and controller configuration require deployment evidence.
\item Relational persistence is designed toward 3NF; intentional snapshots and cross-service
references must be explained. Money is whole XAF (FCFA), not binary floating point.
\item Requirements, UML, test plan, coverage evidence and a third-party setup guide accompany
the source. The combined main report limit is addressed by the pagination policy.
\end{enumerate}
\subsection{Actor semantics}
Roles are \code{super_admin}, \code{admin}, \code{staff} and \code{student}.
``Instructor'', ``finance officer'' and ``HR manager'' are business responsibilities,
not additional implemented role enum values. Staff privileges are broad in some
modules; fine-grained departmental permissions are not implied. An HR employee is a
separate domain record whose optional identity link is necessary for self-service.
An institution is the tenant boundary; campus is descriptive context, not a proven
separate campus-level authorization boundary.

\subsection{Operating assumptions}
The reviewed backend targets Python 3.13 container images, PostgreSQL 17 and
RabbitMQ 3.13. It relies on a working sibling frontend build, secure key provisioning,
database migrations, a fee schedule for each relevant program/term and linked
employee accounts. Initial institution/program/term/user provisioning is primarily
through seed or administrative operations, not complete CRUD APIs.
Internet access is necessary only for external provider and deployment dependencies,
not for communication among local ERP containers.

\subsection{Requirement status and priority}
\textbf{Implemented (I)} means a directly corresponding implementation exists;
it does not mean a test was executed during document generation.
\textbf{Partial (P)} means part of the required behavior exists but a stated
acceptance condition, integration boundary or evidence remains missing.
\textbf{Target (T)} means a requirement is not established by the reviewed baseline.
\textbf{Must} is necessary for the brief or for safe operation; \textbf{Should}
is a proposed improvement; \textbf{Optional} is outside mandatory baseline scope.

\subsection{Numbering and change control}
Requirement identifiers in Appendix~\ref{app:catalogue} are stable review handles.
Changing an identifier's meaning requires a revision note, impacted design views,
API/event compatibility assessment and updated acceptance evidence. A proposed
feature must not be reclassified as implemented merely because it appears in a
diagram. Stakeholders must approve new quantitative targets and retention periods.

\subsection{Data rules}
Tenant-owned rows carry \code{institution_id}. Each service validates JWT
claims itself, and sets transaction-local database context. Identity credential
resolution and finance background tasks deliberately use platform context.
Outbox/inbox tables are outside ordinary tenant RLS. Identity enables RLS on
users and refresh sessions, not on institution/campus metadata.
The bootstrap makes service roles database owners; migrations use forced RLS.
This baseline must not be described as separate non-owner runtime and migration
credentials.

User, campus, student, program and enrollment identifiers crossing service
boundaries are opaque UUID references, not distributed foreign keys. Existence and
lifecycle consistency are therefore not guaranteed by the receiving database.
Institution scope is mandatory for ordinary mutations. Time instants should be
timezone-aware; calendar dates and monthly periods must not be confused with instants.
Current monthly summary cutoff follows the worker host's date.

\subsection{Sensitive information}
Credentials, refresh tokens, personal identifiers, salaries, grades and mobile
numbers require least-privilege access. Log redaction, retention, consent, data export
and erasure policies require explicit institutional approval; no jurisdictional
compliance certification is asserted.

\section{Interfaces and business workflow contracts}
\subsection{HTTP contract}
External prefixes are \code{/api/v1/auth}, \code{/api/v1/academic},
\code{/api/v1/finance} and \code{/api/v1/hr}. JSON request/response schemas are
defined with Pydantic. Binary report endpoints return \code{application/pdf}.
UUID identifiers are strings on the wire. Common responses include 200/201,
204 logout, 400 business-input rejection, 401 unauthenticated, 403 forbidden,
404 absent or deliberately concealed object, 409 business conflict, 422 schema
validation and 429 gateway budget exhaustion. Detail payloads are not uniformly
structured; clients must not assume every error is a single string.

Non-production FastAPI instances expose local \code{/docs}, \code{/redoc}
and \code{/openapi.json}. These are not automatically published through the gateway.
Production disables them when the effective environment is actually production.
The SDD contains a generated inventory of all service-local routes, not a fabricated
OpenAPI export.

\subsection{Session contract}
Login returns a ten-minute access JWT and a rotating, HttpOnly refresh cookie.
The refresh session defaults to fourteen days and \code{SameSite=Strict}.
Secure-cookie behavior is configuration-dependent. Base Compose explicitly sets
\code{REFRESH_COOKIE_SECURE=false}; the production override does not reset that
inherited setting. Correct production configuration and TLS are release gates.
Logout revokes the presented refresh session, while already issued access tokens
remain valid until expiry. The frontend keeps access tokens in memory, deduplicates refresh calls within one
JavaScript runtime and redirects after an unrecoverable 401. It has no proactive
expiry timer or cross-tab refresh coordination.

\subsection{Asynchronous contract}
An accepted enrollment and its outbox row commit atomically. The academic worker
publishes \code{academic.enrollment_accepted.v1} to \code{erp.events}.
The finance consumer uses the envelope tenant and fee schedule to create an invoice.
Delivery is at least once; inbox uniqueness and enrollment-level invoice uniqueness
limit duplicate effects. A missing fee schedule leads to a dead-letter queue, not a
zero-value guessed invoice. HTTP enrollment success therefore does not promise
immediate invoice availability.

\subsection{Payment and notification contract}
The backend persists a payment reference before contacting the provider. Provider
status, not callback claims, authorizes settlement. Polling is the viable baseline
when provider callbacks cannot cross the current gateway policy. HR notifications
are persisted records retrieved by polling; email, SMS and push delivery are not
implemented.

\subsection{Test conditions}
Performance acceptance must record host specification, dataset size, duration,
traffic mix, authentication model, pacing and source-IP distribution. The existing
k6 script shares one login token and source IP and measures four read routes.
Its pacing is necessary to avoid measuring only the gateway rate limiter; 25 VUs
are not automatically evidence for 25 independently authenticated user sessions.

Availability percentages, maximum database size, notification latency, accessibility
level and legal retention periods have not been approved. They are intentionally
not invented here. Correctness, isolation and explicit error behavior take precedence
over optimistic uptime or throughput claims.

\section{Verification strategy and acceptance gates}\label{sec:acceptance}
\subsection{Verification methods}
\textbf{Inspection} verifies source, migrations and contracts.
\textbf{Analysis} checks formulas, normalization and dependency boundaries.
\textbf{Test} exercises valid, invalid, cross-tenant, duplicate and concurrent paths.
\textbf{Demonstration} executes the full browser/gateway/broker/database workflow.
Appendix~\ref{app:trace} maps requirements to existing test files and additional
acceptance scenarios. Those scenarios are specifications, not newly executed tests.

\subsection{Entry conditions}
Use synthetic tenants and users with all four roles; provision migrated service
databases and signing keys; create matching program/term/fee schedules; register
students in course offerings; link employees to identity users; select a deterministic
payment test double or an explicitly authorized sandbox. Never execute destructive
recovery drills against a shared production database.

\subsection{Exit conditions}
\begin{enumerate}
\item All Must requirements are implemented or have an explicit, instructor-approved
exception. Partial and target items remain visible in the submission.
\item Required tests pass against the identified commit with stored reports and
coverage evidence. Critical cross-module flows are demonstrated through the gateway.
\item Load results meet approved conditions or are honestly reported as a failed gate.
\item Payroll rates have authoritative, period-specific review; example data is not
used for real payments. Provider integration is accurately labeled mock or sandbox.
\item A representative recovery test verifies all databases, events, sessions and
financial invariants. Scheduled off-host backup is established before real records.
\item Effective production Compose settings, TLS, secrets, image publication, CI
triggers and promotion workflow are verified in the actual target environment.
\end{enumerate}

\subsection{Defect and evidence management}
Record requirement ID, expected/observed behavior, reproduction, severity, owner,
commit and retest evidence for each issue. Existing documentation names unresolved
work but is not a replacement for the required issue tracker board.
The release authority must approve documented exceptions; this draft does not grant them.

\callout{Evidence integrity}{Only document and diagram builds are executed as part of
this deliverable. Historical performance and recovery values are quoted with their
limitations. No application test pass count, coverage percentage, production deployment
or sandbox transaction is claimed without a corresponding run artifact.}

\section{Detailed requirements catalogue}\label{app:catalogue}
All acceptance conditions below are to be verified at the stated scope. Evidence
paths are repository-relative. A path identifies implementation or test material,
not a claim that it passed. Source origins: AUTH/DATA/INT/OPS derive from brief
section A; ACAD/FIN/HR derive from section B; DOC from sections C/D and the checklist.

\subsection{Identity, access and tenant context}
\req{AUTH-01}{Secure login}{\statusI}{Must}
{The identity service shall authenticate active accounts using Argon2 password
verification and return an RS256 access token only after successful verification.}
{Correct credentials return 200 and token metadata; incorrect or inactive-account
credentials return 401. Password plaintext shall not be persisted. Email lookup
uses the normalized lowercase value.}
{services/identity/app/routers/auth.py}
\req{AUTH-02}{Token lifetime and claims}{\statusI}{Must}
{Access tokens shall have a default lifetime of ten minutes and carry identity,
role and tenant/campus context; resource services shall independently verify signatures,
issuer, audience and expiry.}
{Expired, wrong-key, wrong-issuer and wrong-audience tokens return 401 at protected
routes. A spoofed tenant header shall not override a valid token's tenant.}
{services/identity/app/core/security.py}
\req{AUTH-03}{Refresh rotation}{\statusI}{Must}
{A valid refresh request shall revoke the used refresh row, create a replacement in
the same family and return a new access token; only refresh-token hashes shall be stored.}
{Sequential reuse of an already revoked token returns 401 and revokes the remaining
active family. A replacement token works before expiry. Concurrent-refresh behavior
requires a separate race test; it is not inferred from sequential coverage.}
{services/identity/tests/test_auth.py}
\req{AUTH-04}{Lockout}{\statusI}{Must}
{Five failed password checks shall trigger a default fifteen-minute account lockout;
successful login after the permitted time shall reset the failure state.}
{Attempts during the lockout return 401 even with correct credentials. Verify exact
threshold and recovery using controlled time; the gateway has an independent login budget.}
{services/identity/app/core/config.py}
\req{AUTH-05}{Logout and client expiry}{\statusP}{Must}
{Logout shall revoke the presented refresh session and clear its cookie. The UI
shall end an unauthenticated session when tokens can no longer be refreshed.}
{Logout returns 204. Subsequent refresh is rejected. Existing access tokens remain
valid until their own expiry; immediate access-token revocation is not promised.
The frontend implements 401-driven refresh/redirect; test network-error logout
and multiple tabs separately before declaring complete session-lifecycle acceptance.}
{services/identity/app/routers/auth.py}
\req{AUTH-06}{Role and ownership enforcement}{\statusP}{Must}
{At least four roles shall be enforced at API and UI layers, with object ownership
checks for student and employee self-service.}
{Run the Section 4 role matrix across two tenants. Forged object identifiers must not
reveal another student's invoices or employee's private records. API checks and page-level role checks exist. Navigation remains visible to all
authenticated roles; unsupported role/module combinations display placeholders
rather than full administrative screens.}
{services/hr/app/deps.py}
\req{AUTH-07}{Tenant-scoped persistence}{\statusI}{Must}
{Ordinary tenant requests shall use verified institution context and forced RLS on
scoped business and Identity user/session tables; service database roles shall not
connect to other service databases.}
{A tenant-A request cannot read/write tenant-B rows in protected tables; each runtime
role fails a connection attempt to another service database. Outbox/inbox tables,
Identity institution/campus metadata and platform-context flows are explicit exceptions.}
{tests/integration/test_db_isolation.py}
\req{AUTH-08}{Production session configuration}{\statusP}{Must}
{Production browser sessions shall use HTTPS and Secure, HttpOnly, SameSite refresh
cookies; the deployment configuration shall not inherit development overrides.}
{Inspect the effective merged deployment, perform a browser login over HTTPS and
inspect cookie attributes. This is not currently established by the production
override, which leaves base environment and cookie settings in place.}
{docker-compose.prod.yml}
\req{AUTH-09}{Administrative MFA}{\statusT}{Optional}
{If adopted, administrators shall perform a second authentication factor before
privileged access, with recovery and audit controls.}
{An approved factor, enrollment/recovery policy and positive/negative tests are
required before activation. No OTP or MFA endpoint exists in the baseline.}
{services/identity/app/routers/auth.py}

\subsection{Academic management}
\req{ACAD-01}{Program and course lifecycle}{\statusP}{Must}
{Authorized staff shall manage programs and courses through create, read, update and
delete/archive operations that preserve referenced academic records.}
{Program list and course create/list exist. Complete program creation/update/removal
and course update/removal require implementation and lifecycle acceptance; seed
scripts shall not be presented as complete CRUD APIs.}
{services/academic/app/routers/courses.py}
\req{ACAD-02}{Enrollment acceptance}{\statusI}{Must}
{A student shall enroll only themselves; admin/staff may enroll a specified student.
Acceptance shall atomically persist the enrollment and a billing event outbox row.}
{Valid same-tenant program/term returns 201; missing references return 404; repeat
student/program/term returns 409 in the normal duplicate path. Rolled-back acceptance
shall leave neither record. Campus/student external existence is not cross-database verified.}
{services/academic/app/routers/academic.py}
\req{ACAD-03}{Prerequisite graph}{\statusI}{Must}
{Course prerequisites shall reject self-reference and cycles before insertion.}
{Add A requires B, B requires C; C requires A must return 409. Existing edges must
not duplicate. Rejected edges shall leave the graph unchanged. Concurrent cycle
creation remains a separate verification scenario.}
{services/academic/app/routers/courses.py}
\req{ACAD-04}{Course registration}{\statusI}{Must}
{Student registration shall require their own enrollment, matching program and term,
and a published average of at least 50 percent in an offering of every prerequisite.}
{A score average of 50 passes; an average below 50, unpublished-only results or no
passing offering fails. Duplicate registration returns 409 in the ordinary path.
Capacity is stored but is not an enforced acceptance rule in the baseline.}
{services/academic/tests/test_courses.py}
\req{ACAD-05}{Teaching assignment scope}{\statusI}{Must}
{Teaching mutations shall be limited to admin/super-admin or the assigned staff
instructor of the target offering.}
{Assigned instructor can manage assessments/attendance/exams; unrelated staff and
students receive 403. All checks use the offering from the current tenant.}
{services/academic/app/core/authz.py}
\req{ACAD-06}{Academic attendance}{\statusI}{Must}
{Authorized teaching staff shall create attendance sessions and mark student presence.}
{Create session, record present/absent marks and retrieve results. Current mark entry
does not validate course-registration membership. Summary calculations count all
created sessions, with missing presence marks contributing no attendance credit.}
{services/academic/tests/test_attendance.py}
\req{ACAD-07}{Grades and publication}{\statusI}{Must}
{Teaching staff shall enter assessment scores between zero and the assessment maximum,
and explicitly publish results before student visibility.}
{Out-of-range score returns 400. Student sees only own published scores.
Published scores are still editable through the ordinary grade-entry handler;
immutable grade history is not a delivered general guarantee.}
{services/academic/app/routers/grades.py}
\req{ACAD-08}{Grade appeals}{\statusI}{Must}
{A student shall appeal an owned published grade. Reviews shall transition from
submitted to under-review, accepted or rejected, and from under-review to a final decision.}
{Reject a second open appeal, invalid transition or final-state reopening. Acceptance
requires a bounded corrected score; a changed score writes an audit row in the same
transaction. An unchanged accepted score need not add a score-change row.}
{services/academic/tests/test_grades.py}
\req{ACAD-09}{Exam scheduling}{\statusI}{Must}
{Scheduling and rescheduling shall reject overlapping room, instructor or registered
student usage within an institution/term and serialize conflict checks for that scope.}
{Use overlapping intervals to obtain 409 for each resource conflict. Adjacent intervals
are permitted. Start must precede end. A term advisory lock prevents two concurrent
same-term schedules from both passing conflict checks. Cross-term conflicts are not checked.}
{services/academic/app/routers/exams.py}
\req{ACAD-10}{Reports and at-risk indicator}{\statusI}{Must}
{The system shall export transcript and attendance-summary PDFs and compute a
documented at-risk flag for registered learners.}
{Flag when attendance is below 0.75 OR the mean of the latest two published assessment
percentages is below 50. Fewer than two grades yields no grade-average signal; no sessions
yields no attendance signal. Boundaries 0.75 and 50 are not flagged by that signal.
Students may export only their own reports.}
{services/academic/app/routers/reports.py}
\req{ACAD-11}{Academic dashboards}{\statusP}{Must}
{Students and instructors shall receive current, role-appropriate dashboards using
real enrollment, grade, attendance and at-risk information.}
{Student course cards show live registrations, grades and at-risk values and provide
report downloads. Instructor management and dynamic instructor dashboards remain
placeholders; the overview page only shows a welcome message.}
{services/academic/app/routers/reports.py}

\subsection{Finance and marketing}
\req{FIN-01}{Fee schedules}{\statusI}{Must}
{Finance shall configure a nonnegative whole-XAF fee for an institution/program/term tuple.}
{Authorized admin/staff/super-admin creates one schedule; duplicate tuple returns 409.
Academic references remain opaque IDs. The consumer must use the matched schedule,
never a caller-provided or default price.}
{services/finance/app/routers/finance.py}
\req{FIN-02}{Asynchronous invoice creation}{\statusI}{Must}
{Enrollment events shall produce one invoice effect per institution/enrollment,
with replay handling by event and business identity.}
{Deliver the same event twice, then a distinct event ID for the same enrollment;
verify one invoice. Missing fees must dead-letter without persisting the inbox success
marker. A transient failure must requeue rather than acknowledge a lost invoice.}
{services/finance/tests/test_consumer.py}
\req{FIN-03}{Invoice visibility}{\statusI}{Must}
{Students shall list and retrieve only their own tenant-scoped invoices, with pending
or paid status and amount in XAF.}
{A student requesting another student's invoice receives 404; list filters exclude it.
Enrollment filtering narrows a list without overriding ownership.}
{services/finance/app/routers/finance.py}
\req{FIN-04}{Payment initiation}{\statusI}{Must}
{Payment initiation shall persist a unique provider reference before requesting
payment, and allow at most one pending/succeeded attempt per invoice.}
{Non-pending invoices and a second in-progress intent return 409. A provider-call
failure leaves a pending intent with a logged error rather than falsely marking paid.
Polling checks status; it does not guarantee resubmission of a request never accepted by MTN.}
{services/finance/app/routers/payments.py}
\req{FIN-05}{Atomic settlement}{\statusI}{Must}

\section{Detailed use-case specifications}\label{app:usecases}
\subsection{UC-01 -- Authenticate and maintain a session}
\textbf{Primary actor:} any active user. \textbf{Related:} AUTH-01--05.
\textbf{Precondition:} configured keys and migrated Identity database; account exists.
\begin{enumerate}
\item User submits email/password to the public login endpoint.
\item Identity locates account using platform credential-resolution context, checks
active/lockout status and verifies Argon2 hash.
\item Identity clears failure count, persists a refresh-session hash and returns access
JWT plus refresh cookie.
\item Client sends bearer token for protected operations; gateway delegates verification,
and the target service verifies the token again.
\item At access expiry the client refreshes using the cookie and replaces its access token.
\end{enumerate}
\textbf{Alternatives:} bad credentials increment failures; lockout blocks login;
expired/missing refresh returns 401; reuse revokes the family. Concurrent refreshes
need explicit client/server acceptance. \textbf{Postcondition:} successful session is
identified by claims, not client tenant headers. \textbf{No promise:} immediate invalidation
of issued access tokens on logout.

\subsection{UC-02 -- Enroll and obtain a tuition invoice}
\textbf{Primary actor:} student or authorized admin/staff.
\textbf{Related:} ACAD-02, FIN-01--03, INT-03.
\textbf{Precondition:} valid program/term and separately configured matching fee.
\begin{enumerate}
\item Caller chooses program/term/campus; staff supplies a student ID while student identity
is derived from the token.
\item Academic validates local references and duplicates, then commits enrollment and outbox.
\item HTTP 201 confirms academic acceptance without waiting for Finance.
\item Worker publishes the event with persistent delivery and publisher confirms.
\item Finance consumer inserts inbox ID, finds fee schedule and inserts pending invoice in one transaction.
\item Student polls invoice list by enrollment and views the pending invoice.
\end{enumerate}
\textbf{Alternatives:} broker down leaves outbox unpublished; missing fee sends message to
DLQ and rolls back inbox; transient database failure requeues; duplicate event/enrollment
is acknowledged without another invoice. \textbf{Postcondition:} one accepted enrollment
and eventually one invoice effect when required configuration and infrastructure are healthy.

\subsection{UC-03 -- Register a course with prerequisites}
\textbf{Primary actor:} student. \textbf{Related:} ACAD-03--04.
\textbf{Precondition:} own accepted enrollment, published prerequisite results.
\begin{enumerate}
\item Student selects offering and enrollment.
\item Academic checks ownership, term and course program.
\item Each prerequisite is satisfied by a published percentage average of at least 50
in any offering of that prerequisite course.
\item Academic rejects unmet prerequisites or duplicate registration, otherwise commits 201.
\end{enumerate}
\textbf{Alternatives:} missing/foreign enrollment yields 404; mismatch yields 400; unmet
prerequisites yields 409 with missing course IDs. \textbf{Postcondition:} registration
links student, offering and enrollment. Capacity limiting is not currently enforced.

\subsection{UC-04 -- Publish and appeal a grade}
\textbf{Actors:} assigned instructor/admin and student. \textbf{Related:} ACAD-05,07,08.
\begin{enumerate}
\item Instructor creates an assessment, enters bounded scores and explicitly publishes.
\item Student retrieves an own published grade and submits an appeal with a reason.
\item Authorized reviewer moves appeal under review or decides directly.
\item Acceptance supplies corrected score; changed values append grade audit history.
\item Appeal decision, metadata and correction commit together.
\end{enumerate}
\textbf{Alternatives:} unpublished/foreign grade cannot be appealed; duplicate open appeal
is rejected; final states cannot reopen; correction beyond maximum is rejected.
\textbf{Postcondition:} decision is persisted and, if changed through appeal, score history
is recorded. Ordinary grade edits remain outside this audit guarantee.

\subsection{UC-05 -- Settle tuition and retrieve receipt}
\textbf{Actor:} student; supporting actor is the selected payment provider.
\textbf{Related:} FIN-03--07.
\begin{enumerate}
\item Caller selects a pending owned invoice and submits payer mobile number.
\item Finance commits intent/reference, then calls request-to-pay.
\item Client GET or three-second worker polling asks provider status.
\item Pending leaves business state unchanged; failed marks intent failed.
\item Success locks intent and invoice, marks paid, posts balanced entries and adds receipt,
then commits all changes.
\item Caller downloads receipt PDF.
\end{enumerate}
\textbf{Alternatives:} provider timeout leaves pending, not paid; GET errors may surface;
duplicate reconciliation is a no-op for terminal intent. A callback is only a hint to
query provider status; current gateway prevents unauthenticated provider ingress.
\textbf{Postcondition:} paid status is backed by ledger and receipt, not by browser assertions.

\subsection{UC-06 -- Schedule an exam safely}
\textbf{Actor:} authorized instructor/admin. \textbf{Related:} ACAD-09.
Actor supplies offering, room and start/end. Backend verifies authority and interval,
locks institution/term scheduling, tests room, instructor and shared-student overlap,
then persists or returns 409. Rescheduling excludes the current record from conflicts.
The submitted offering field does not change the existing offering during reschedule.
Adjacent intervals are allowed; cross-term overlap is outside the implemented search.

\subsection{UC-07 -- Request leave and notify the employee}
\textbf{Actors:} linked employee and different HR approver. \textbf{Related:} HR-04--05.
Employee submits dates/reason; HR sees pending request and approves or rejects;
backend rejects self-approval and already-decided requests, then writes decision
and in-app notification in one commit. The employee polls notifications and marks
the notice read. Unlinked employees cannot use self-service. There is no email
delivery guarantee, automatic quota enforcement or working-day calculation.

\subsection{UC-08 -- Generate and approve payroll}
\textbf{Actors:} HR administrator and rate-verifying super administrator.
\textbf{Related:} HR-07--09.
An HR administrator creates an unverified rate version and generates a draft
period run for active employees. Calculation uses the selected version, not an
implicit statutory default. A super administrator checks authoritative sources
and attests the schedule. HR approves the draft only after verification; employees
retrieve their own saved payslips. A repeated period fails and unverified approval
returns 403. Approval records a decision; it does not transfer money.

\subsection{UC-09 -- Record employee attendance}
\textbf{Actors:} HR administrator and linked employee. \textbf{Related:} HR-03.
HR creates a shift and issues a token through the API; the employee UI accepts the
token as pasted or typed text.
Issuing another token replaces the stored token ID. Employee submits token with
an ERP bearer session; backend checks QR signature/expiry/current ID, shift ownership
and uniqueness before recording check-in. Expiry/replacement yields 401; repeated
check-in yields 409. Camera scanning and QR image issuance screens are not implemented.

\subsection{UC-10 -- Control stock movements}
\textbf{Actor:} HR administrator. \textbf{Related:} HR-10.
Actor selects asset, delta, optional employee and reason. Backend locks asset,
calculates aggregate assignments and rejects a movement that exceeds stock or
reduces total stock below assignments. Employee-linked deltas alter assignment balance;
unlinked deltas alter total quantity. Commit preserves movement history.
Employee-specific over-return prevention needs additional rules beyond the aggregate check.

\subsection{Critical acceptance scenario set}
\begin{enumerate}[label=AT-\arabic*]
\item \textbf{Tenant escape negative test:} seed tenant A/B, use A's token with B's resource
ID and spoofed headers; verify no B data is returned or modified.
\item \textbf{Broker outage:} disable only a disposable test broker after setup; enroll;
verify committed outbox and no synchronous dependency; restore broker and obtain one invoice.
\item \textbf{Consumer replay:} deliver duplicate event ID and duplicate enrollment under
a new event ID; verify one invoice and visible missing-fee DLQ behavior.
\item \textbf{Settlement atomicity:} reconcile the same success from two callers, inject
failure before commit and inspect intent/invoice/receipt/ledger invariants after retry.
\item \textbf{Exam conflicts:} schedule overlapping room, instructor and common-student
exams; verify rejection and adjacent-slot acceptance under simultaneous requests.
\item \textbf{Payroll release gate:} create an unverified schedule, generate a draft,
attempt approval, attest using reviewed source evidence, then approve.
\item \textbf{Recovery:} restore an isolated representative ERP cluster to a known time,
reconcile queue/outbox state and revoke obsolete sessions before service restoration.
\item \textbf{Production configuration:} inspect effective merged settings and externally
observed cookie/TLS/listener behavior; do not rely on comments in override files.
\end{enumerate}
